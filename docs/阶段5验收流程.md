# 阶段 5 验收流程：TCP 流重组与跨段 HTTP/TLS

本阶段解决“一个 HTTP 请求或 TLS 握手被拆成多个 TCP 包，单看一行看不全”的问题。程序把同一会话的片段按序号整理，并告诉你哪些字节连续、哪些地方缺包或冲突。先用固定的离线样例审核，会比直接看浏览器产生的大量包容易。

本次审核使用新项目 `sniffer_1a_git`。不需要重新安装 Python、Npcap 或依赖，也不需要切换网卡；离线样例审核不产生网络流量。

.\.venv\Scripts\python.exe -X utf8 .\examples\make_stream_demo.py

生成脚本应提示“已生成 31 个完全合成的离线数据包”，文件位置是：

```text
D:\研一课程\软件与系统安全\sniffer_1a_git\examples\stage5_tcp_demo.pcap
```

若提示“文件已存在，未覆盖”，直接使用该文件即可。只有明确要重新生成时才执行下面的命令；它会覆盖这个合成样例文件：

- 如果当前窗口已有数据，先保存需要保留的数据，再确认替换。
- 等待状态恢复“已停止”，确认“当前显示 31 / 保留 31”。

- 核对摘要显示 **5 条流、2 个可见域名**。在表格右侧应出现“TCP流”“流方向”“流状态”三列；看不见时向右滚动表格。

此时只有 TCP 流分析，表格应有 11 列；尚未点击“分析域名”不影响本次审核。

如果详情区域太矮，可以向上拖动表格与详情之间的分隔线，为文字留出更多空间；详情也可以上下滚动。

## 先看能正确拼出的两条流

定位方法统一为：协议选“全部”，IP 和域名框留空，在“端口”框输入下表端口，再点击“应用筛选”。这里端口会匹配源端口或目的端口，所以两个方向都会显示。

| 端口 | 预期显示数量 | 原始编号 | 应看到的内容 |
| --- | ---: | --- | --- |
| `51001` | 9 包 | #1～#9 | IPv4 HTTP，跨段域名 `www.stage5.example.test` |
| `51002` | 9 包 | #10～#18 | IPv6 TLS，跨段域名 `tls.stage5.example.test` |

输入 `51001` 后，选择表格中的任意一行，在下方详情顶部查看“TCP 流追踪”：

- 同一组包应使用同一个流编号，两个方向分别显示 `A→B` 和 `B→A`。
- 详情应显示 `www.stage5.example.test`，证据来源为 `HTTP Host`。
- 查看“连续载荷贡献包”和“重复字节”。样例故意让尾段先到，再发送头段并重复头段；程序应能恢复 Host，并记录重复字节。
- “流内原始包”仍是原始编号 #1～#9，不因筛选变成另一组编号。

然后把端口改成 `51002` 并再次“应用筛选”：

- 详情应显示 IPv6 端点，地址和端口用 `[IPv6地址]:端口` 的形式区分。
- 应看到 `tls.stage5.example.test`，证据来源为 `TLS SNI`。
- ClientHello 被拆成三个 TCP 片段，单个片段不具备完整 SNI 消息；流分析应能恢复它。

这里的 TLS SNI 是握手里可见的名称，**不表示程序解密了 HTTPS 网页、账号或正文**。样例域名以 `.test` 结尾，只用于离线教学，不需要在浏览器访问。

## 再看必须拒绝确定域名的三条流

继续只改变“端口”条件，每次点击“应用筛选”：

| 端口 | 预期显示数量 | 原始编号 | 核对重点 |
| --- | ---: | --- | --- |
| `51003` | 5 包 | #19～#23 | SYN 后缺少 7 个字节；应提示缺口，不发布可确认的跨段域名 |
| `51004` | 6 包 | #24～#29 | 两次捕获的重叠 Host 字节不同；应提示冲突，不发布可确认的跨段域名 |
| `51005` | 2 包 | #30～#31 | 没捕到 SYN，起点未知；应显示流信息，但不发布可确认的跨段域名 |

“缺口”是 TCP 序号显示中间应有字节，但这份抓包里缺少它；“冲突”是同一个序号位置出现了不同字节；“起点未知”是抓包可能从连接中途开始。程序应展示这些限制，不能仅因为某个片段看起来像完整 HTTP 请求就断言整个流可靠。

某一行属于返回方向时，“流状态”列可能显示该方向的 FIN/RST 状态。判断整个流是否可靠，请看详情中的**会话状态及说明**，不要只看一条返回包的方向状态。

## 核对域名分析和流分析相互独立

- 点击“重置筛选”，确认恢复全部 31 包。
- 点击“分析域名”，等分析完成。表格应保留三列 TCP 流信息，并增加“域名”“依据”，总计 13 列。
- 记录“DNS统计”标签的完整文本，再点击“追踪 TCP 流”。完成后，DNS 统计文本应保持不变。
- 随意筛选 `51001` 或 `51002`，DNS 统计仍不应随显示包数变化。

该样例没有 DNS 查询/响应，因此 DNS 查询、响应、匹配事务、未匹配查询均应为 0；“唯一直接域名”统计也包含阶段 4 单包 HTTP/TLS 证据，不能把它简单理解为 DNS 查询过的域名数。

**阶段 4 的“域名”筛选仍使用阶段 4 的证据。** 它不会自动把阶段 5 拼出的域名纳入筛选。审核跨段证据时使用上述端口条件，再看“TCP 流追踪”详情。

阶段 4 可能在 #22、#27、#30 之类的完整单包 HTTP 文本中显示 Host，但相应流仍因缺口、冲突或没看到 SYN 而拒绝确定的跨段证据。这不矛盾：前者读取本包字段，后者检查整个流的连续性。

表格列数可按下表核对：

| 当前分析状态 | 总列数 |
| --- | ---: |
| 刚导入，尚未分析 | 8 |
| 仅“分析域名”完成 | 10 |
| 仅“追踪 TCP 流”完成 | 11 |
| 两种分析都完成 | 13 |

## 核对保存不受筛选影响

- 保持端口 `51002` 的筛选，界面应显示 **9 / 保留 31**。
- 点击“保存 pcap”，保存为新文件，例如 `stage5_review_saved.pcap`。不要覆盖自己的真实抓包文件。
- 等待保存完成，状态应提示保存了 **31 个数据包**。
- 点击“打开 pcap”，重新打开刚保存的文件；点击“重置筛选”。应再次显示 **31 / 保留 31**。
- 重新“追踪 TCP 流”，应再次得到 5 条流、2 个可确认域名。

保存内容只有原始数据包，流编号、域名证据和界面统计不会写进 PCAP。重新打开后需要重新分析。自动化测试还会检查原始包字节不被分析改写。

## 核对清空、导入和取消

- **成功导入：** 有流结果时重新打开样例文件，旧流列应消失，摘要恢复“TCP流：尚未分析”；点击分析后重新出现。
- **清空：** 点击“清空”，应清除包、流结果和域名结果，恢复 8 列、实时模式。
- **继续抓包：** 实时模式有数据并完成流分析后，再次“开始抓包”会清除旧流结果；停止并排空后可以重新分析。文件模式下不能直接继续抓包，须先清空。
- **导入失败：** 已有有效结果时，尝试打开一个普通 `.md` 文件（在文件选择框切到“所有文件”）。程序应提示文件格式错误，原来保留的包和流结果不应被替换。
- **取消流分析：** 分析中“停止”按钮会显示为“取消流分析”。点击后等待线程退出；不应出现半成品流结果。若此前已有有效流结果，应保留上一次结果。
- **关闭：** 分析中关闭窗口时，程序应请求取消并等待后台退出，再关闭，不出现线程销毁错误。

31 包可能很快分析结束，来不及点击取消属于正常情况。取消、失败、陈旧结果和分析中关闭由下面的 GUI 自动化测试稳定验证，不必为了点中按钮重复操作很多次。

## 真实浏览器抓包的预期

固定样例通过后，可以选择正在联网的网卡，**先开始抓包，再打开网页**，停止并排空后进行流分析。浏览器可能复用已有连接，也可能使用 QUIC/HTTP3 或 ECH，所以不保证每次访问都能看到 SYN 或明文 SNI。没有流域名不等于程序一定出错，也不表示该连接与网站无关。

默认上限为 10000 个输入包、1024 条会话、每流 4096 个片段、每方向 2 MiB 缓存载荷、总计 32 MiB 缓存载荷。预算保守计入重复捕获的载荷字节，达到限额会提示，受限流不提供确定域名；序号跨度也受限。预算不是整个程序内存的硬上限。

本阶段不进行 IP 分片重组、HTTPS 解密、QUIC/HTTP3 分析、进程追踪或外部域名查询；FIN/RST 状态只反映抓包里观察到的边界，不等同于完整 TCP 协议栈或 Wireshark 的所有分析功能。
